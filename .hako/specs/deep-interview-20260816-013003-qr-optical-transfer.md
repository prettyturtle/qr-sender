## § 치명 결함 — rev2의 스케줄러 모델은 성립하지 않았다

rev2의 확정 G는 "송신자가 세그먼트별 방출 예산을 채우면 윈도우를 전진한다"였다. 여기 숨은 가정이 **캡처율 r = 1**이다. 그런데 r은 항상 1보다 작다.

```
r = 수신 디코드 fps / 송신 재생 fps
  Android 8/10 = 0.8   ·   데스크톱 6/10 = 0.6   ·   iOS 4/10 = 0.4
```

송신자가 세그먼트 S에 예산 B를 쏟고 윈도우를 전진하면, r=0.4인 수신자는 그중 0.4B만 잡는다. 복원에 못 미치므로 **전체 파일이 한 바퀴 돌아 S가 다시 올 때까지 부분 심볼을 들고 대기**한다. 그 결과:

1. **수신자 메모리 상한이 붕괴한다.** rev2는 송신자 버퍼만 W로 묶었을 뿐, 수신자는 윈도우가 아니라 **파일의 모든 세그먼트**에 대한 부분 집합을 동시에 들고 있게 된다.
2. **완료가 전부 끝에 몰린다.** 어떤 세그먼트도 중간에 완성되지 않아 점진 복원·미리보기·이어받기 UX가 전부 무의미해진다.
3. rev2의 "전체 스트림 중간진입 페널티 ≤ 윈도우 1회 추가 스윕"은 r=1에서만 참인 명제였다.

**해소**: 윈도우를 없애고 **전 세그먼트 라운드로빈**으로 간다. 그리고 systematic RS를 쓰면 문제 1이 자동으로 사라진다 — 아래에서 설명한다.

## § 핵심 설계 — 캐러셀 + systematic Reed-Solomon

### 왜 파운틴을 버리는가

K ≈ 100~200은 파운틴 코드가 유리한 영역(K ≥ 10⁴)이 아니다. robust soliton LT의 실측 오버헤드는 이 영역에서 1.3~1.6×인데, **MDS 코드인 RS는 정상 조건에서 정확히 1.0×**다.

| 조건 | LT | 캐러셀 RS |
|---|---|---|
| 정상 조준 | 1.3~1.6× | **1.0×** |
| 손실 ≤ (N−K)/N | 1.3~1.6× | **1.0×** |
| 고손실 (>40%) | 우세 | 열세 (추가 사이클) |

고손실 영역은 이 제품의 실사용 체제가 아니다 — 그 조준 상태면 코칭 UI가 개입해야 할 상황이다.

### 파생 이득 4가지

**1. 송·수신 동기화 계약이 0이 된다.**
LT는 `frameSeed`로 송·수신이 동일 PRNG·동일 degree 분포를 **비트 단위로 재현**해야 했다. PWA에서 이건 특히 위험하다 — Service Worker 캐시 때문에 송신자 v1.2 / 수신자 v1.3 스큐가 일상적으로 발생하는데, 분포가 한 번이라도 바뀌면 크로스 버전 전송이 **조용히** 깨진다.

RS는 `symIndex`를 헤더에 명시한다. 수신자는 헤더만 읽으면 되므로 **송신자가 어떤 순서로 방출하든 무관하다.** 패스마다 인덱스를 셔플해 주기적 드롭아웃 상관을 깨도 수신자는 영향받지 않는다.

**2. 수신자 메모리 증폭이 사라진다.**
systematic RS는 symIndex < K인 심볼이 **원본 데이터 그 자체**다. 곧바로 출력 버퍼에 꽂힌다. 별도 보관이 필요한 것은 리페어 심볼뿐이고, 그마저 세그먼트가 복원되는 즉시 폐기된다.
→ 수신자 메모리 ≈ **출력 파일 크기** (어차피 불가피한 양). LT는 인코딩된 XOR 조합을 1.3× 들고 있어야 했다. 위 치명 결함의 문제 1이 여기서 자동 해소된다.

**3. 이어받기 직렬화가 비트맵 하나로 축소된다.**
rev2의 "LT 부분 디코딩 행렬 상태 직렬화" → **세그먼트당 N비트 수신 비트맵 + 리페어 심볼 원본**.

**4. 진짜 점진 복원이 가능해진다.**
systematic 심볼이 도착하는 즉시 파일의 해당 구간이 채워지므로, 텍스트·이미지는 **구멍 뚫린 상태로 미리보기**가 가능하다.

### rev2가 인덱스 순환을 기각한 근거는 과장이었다

rev2의 D1은 "특정 인덱스가 글레어로 반복 손상되면 영원히 미완성"을 이유로 인덱스 방식을 버렸다. 재검토 결과 **성립하지 않는다** — QR은 매 프레임 화면의 같은 영역을 차지하므로 글레어는 **공간적** 현상이고, 인덱스는 **시간적** 순서다. 둘이 상관될 구조적 이유가 없다. 만약을 대비해 패스마다 방출 순서를 셔플하면(위 이득 1에 의해 무비용) 어떤 주기적 상관도 깨진다.

### base44 — 왜 공짜인가

base45가 2바이트를 3문자에 담는 근거는 `45³ = 91,125 ≥ 65,536` 이다. 그런데:

```
44³ = 85,184  ≥ 65,536   ✓   (3문자 / 2바이트 패킹 그대로 성립)
44²  = 1,936  ≥ 256      ✓   (트레일링 1바이트도 성립)
```

QR alphanumeric 45자 집합에서 **공백만 제거한 44자** (`0-9 A-Z $ % * + - . / :`) 를 쓰면 밀도 손실이 **정확히 0**이면서 플랫폼 API의 선행·후행 공백 트림 리스크가 사라진다. 잃는 것은 RFC 9285 라이브러리 재사용뿐이고 코덱은 약 30줄이다.

### 용량 계산

| 항목 | 값 |
|---|---|
| V25 / ECC-L alphanumeric 용량 | ~1,852 chars |
| base44 실효 용량 (`⌊1852/3⌋ × 2`) | **1,234 B** |
| 헤더 (D2) | 24 B |
| **프레임당 페이로드** | **1,210 B** |
| K (SP-B 산출, 초기 후보) | **96** |
| N | **255** (GF(256) 상한) |
| 세그먼트 크기 | `96 × 1,210` = **116,160 B** ≈ 113 KB |

### K 선정 제약 — 이게 스케줄 설계의 핵심 조건

전 세그먼트 라운드로빈에서 한 사이클은 세그먼트당 N개 심볼을 방출한다. 캡처율 r인 수신자는 사이클당 `r × N` 개를 잡는다. **한 사이클 안에 복원되려면:**

```
r_min × N ≥ K
```

`r_min = 0.4` (iOS 4fps / 재생 10fps), `N = 255` → **K ≤ 102**.

이 조건이 만족되면:

| 수신자 | 사이클당 획득 | 필요 | 완료 시점 | 오버헤드 |
|---|---|---|---|---|
| r=1.0 | 255 | 96 | 사이클의 38% | **1.0×** |
| r=0.8 (Android) | 204 | 96 | 사이클의 47% | **1.0×** |
| r=0.4 (iOS) | 102 | 96 | 사이클의 94% | **1.0×** |

**모든 캡처율에서 오버헤드 1.0×이고, 빠른 수신자가 유휴 상태가 되지도 않는다.** 모든 세그먼트가 동시에 진행되므로 어떤 프레임도 낭비되지 않는다. rev2의 윈도우 방식이 풀지 못한 브로드캐스트 딜레마가 여기서 해소된다.

> r < 0.376 (예: iOS가 3fps만 낼 때)이면 2사이클이 필요하고 오버헤드는 ~1.6×로 열화한다. SP-B가 이 경계를 실측하고 K를 확정한다.

### 방출 순서

```
for j in shuffle(0 .. N-1):          # 패스마다 셔플 (수신자는 영향 없음)
    for s in 0 .. segCount-1:        # 전 세그먼트 라운드로빈
        emit(segIndex=s, symIndex=j)
반복 (무한 루프)
```

- 파일 읽기 최적화: `j` 를 8개씩 묶어 세그먼트당 8심볼 버스트로 방출하면 `File.slice()` 읽기가 8배 줄어든다. 균일성 손실은 무시 가능.
- 송신자 메모리: 현재 세그먼트 1개(113KB) + RS 인코딩 버퍼 = **O(1)**, 파일 크기 무관.
- 리페어 심볼 계산: `repair_j = Σ g_{j,i} · source_i` (i = 0..K−1). 세그먼트 하나를 읽어 GF(256) 선형결합. 프레임당 `96 × 1,210 ≈ 116K` GF 연산 → 10fps에서 1.2M ops/s, 무시 가능.
- 수신 디코딩: erasure decode = K×K 행렬 역변환(96³ ≈ 884K GF ops) + `K² × 1,210 ≈ 11M` GF mul-add → 워커에서 세그먼트당 수십~수백 ms. 세그먼트 수신에 수십 초가 걸리므로 병목 아님. **결손이 0이면 디코딩 자체가 불필요** (systematic).

## Stage 0 — 디리스킹 스파이크 (차단성)

rev2는 스파이크 3개를 전부 차단성으로 묶었으나, 실제 차단성은 **아키텍처를 바꾸는 것**뿐이다. fps 측정은 수치 조정급이며 본 개발 M4에서 부산물로 나온다.

### SP-A · `BarcodeDetector` 문자 충실도 — 차단성, 기기 없이 검증 가능

**검증 대상**: base44 문자열이 `BarcodeDetector.rawValue` 를 무손실 통과하는가.

- `detect()` 는 `ImageBitmapSource` 를 직접 받으므로 **카메라 없이 canvas 주입**으로 검증된다
- 적대적 케이스 우선: 선행/후행 공백 유사 문자, 44자 알파벳 전수 스윕, 만재 프레임 랜덤 100개
- 자기완결 정적 HTML 페이지로 만들어 pass/fail을 화면 표시 → **Samsung Remote Test Lab(무료)·BrowserStack·지인 기기** 어디서든 링크 하나로 실행
- ⚠️ 데스크톱 Chrome도 `BarcodeDetector` 를 노출하지만 백엔드가 Android(GmsCore/MLKit)와 다르다 — 스모크일 뿐 대체 아님

**실패 시**: `zxing-wasm` 단일 경로로 전환 → D8·AC-1e·OQ-1 삭제, D4 용량표를 byte 모드(1,249B)로 재산정. **스펙 표면적이 오히려 줄어든다.**

### SP-B · 스케줄러 × 캡처율 × 중간진입 몬테카를로 — 차단성, 순수 계산

rev2의 SP-3(LT 고립 측정)를 **비교 시뮬레이션**으로 재설계한다. 선택을 검증하는 게 아니라 선택지를 고른다.

**시뮬레이션 축**:
- 코딩: `캐러셀 RS(K,N)` vs `LT(robust soliton)` — 동일 하네스에서 비교
- 캡처율 r ∈ {0.3, 0.4, 0.6, 0.8, 1.0}
- 중간 진입 오프셋: 사이클의 0~99% 균등
- 프레임 손실률 p ∈ {0, 0.1, 0.2, 0.4}
- 세그먼트 수 S ∈ {1, 10, 90, 180}
- K ∈ {64, 96, 128, 180} × N = 255

**산출물**:
1. `(K, N)` 확정값 — `r_min × N ≥ K` 를 만족하면서 세그먼트 오버헤드를 최소화
2. 코딩 방식 최종 확정 (RS가 진다면 그 근거)
3. 수신자 피크 메모리 (세그먼트별 미복원 리페어 심볼 보유량)
4. 오버헤드 p50 / p95 표 → **확정 B의 ETA 모델에 직접 배선**

> **이 시뮬레이터는 폐기하지 않는다.** RS 인코더·디코더·스케줄러의 순수 형태이며 그대로 `src/core/` 제품 코어가 된다. rev2의 "스파이크 코드는 버린다" 규칙은 최대 산출물을 버리는 규칙이었다.

### 차단성이 아닌 것 (M4로 이월)

| 항목 | 이유 |
|---|---|
| **iOS Safari fps 실측** | 실패 파급이 "V20 하향 + 프레임 홀드 연장"인데 V20~V30 적응은 이미 A5에 있고 헤더 계약·코더 코어 불변. 하네스도 M4의 최소 수신 페이지와 동일물 — 두 번 만들 이유 없음 |
| **`BarcodeDetector` vs `zxing-wasm` fps A/B** | 광학 경로 필수라 원격 대체 불가. M4 최소 페이지에서 부산물로 나옴. **단 A/B 측정 자체는 반드시 수행** — 격차 15% 이내면 zxing 단일 경로로 접고 표면적을 줄인다 |

### Stage 0 종료 조건

SP-A · SP-B 결과 문서가 `.hako/specs/spike-*.md` 로 존재하고, D1·D2·D4·D8·확정 B가 그 수치로 재확정될 것.

## 확정 사항

### A. 제품 형태 — 공개 무료 웹툴 (PWA)

링크 하나로 누구나 쓰는 정적 호스팅 PWA. 모르는 사람도 온보딩 가능해야 하고 모바일 브라우저 호환성이 1급 요구사항.

### B. 용량 정책 — 검증 상한 20MB, 초과 시 경고 후 진행

크기 자체를 막지는 않되 **검증된 범위를 정직하게 알린다.**

```
✅  ~20 MB   검증됨
⚠️  20 MB+   "이 크기는 검증되지 않았습니다. 예상 소요 1시간 이상" — 진행은 가능
```

ETA는 **수신 기기별 범위**로 표시한다 (D6 = 1.0× 반영):

| 수신 경로 | 디코드율 | goodput | 10MB 소요 |
|---|---|---|---|
| Android Chrome (`BarcodeDetector`) | 8 fps | **9.7 KB/s** | **18분** |
| 데스크톱 Chrome 웹캠 | 6 fps | **7.3 KB/s** | 24분 |
| iOS Safari (`zxing-wasm`) | 4 fps | **4.8 KB/s** | **36분** |

```
10 MB  →  약 18 ~ 36분  (수신 기기에 따라)
```

> 이 소프트 상한 하나가 **OQ-4(송신 측 파일 읽기 전략)와 OQ-5(장시간 미검증)를 동시에 해소한다.** 20MB 이하면 메모리 상주로 충분하므로 `File` 핸들 유효성 문제가 소멸하고, "송신 측 이어받기"가 조건부에서 무조건 제외로 단순해진다.

### C. 릴리스 범위 — Stage 0 이후 재확정 (잠정)

| 항목 | 상태 | 판단 |
|---|---|---|
| 파운틴/RS 스트리밍 + 뷰어 | **필수** | 제품의 존재 이유 |
| **이어받기** | **필수 · 최우선** | iOS에서 10MB가 36분인 현실에서 사실상 필수 |
| 수신 코칭 UI | 필수 | AC-9 성패가 여기 달림. 비용 저 |
| 암호화 | 필수 | 프라이버시가 세일즈 포인트인 제품에서 신뢰 가치 높음. WebCrypto라 비용 중 |
| **2×2 그리드** | **실험 트랙으로 강등** | 아래 |

**2×2 그리드를 뺀 이유**: (1) 전제 능력(4심볼 동시 검출)이 유일하게 미검증인 항목이면서 스파이크도 없다. (2) 27인치 1440p + 모듈당 3px 실측이라는 최고 비용의 실기기 리그를 요구한다. (3) 수혜 조합이 "데스크톱 송신 + 고해상 카메라"로 가장 좁고, 60% 동시 검출을 스스로 인정하는 시점에서 실효 이득은 4×가 아니라 2× 미만이다. (4) rev2의 전환 판정이 CSS px 기준이라 devicePixelRatio 높은 13인치 노트북에서 물리 크기 부족과 자체 충돌한다.

**단 D12의 emitter/renderer 분리는 유지한다** — 기능은 빼되 추상화는 남긴다.

### D. 지원 범위 — 모든 조합 대칭

데스크톱↔모바일 양방향, 폰↔폰 전부. iOS Safari 포함. 디코더는 `BarcodeDetector` → `zxing-wasm` 이중 경로이되 D8에 의해 두 경로의 바이트 충실도가 동일해야 한다 (SP-A가 증명, M4 A/B가 유지 여부를 결정).

### E. 복원 단위 — 균일 세그먼트

`segmentSize = K × 1,210 B` (SP-B가 K 확정). `segCount = ceil(fileSize / segmentSize)`. 마지막 세그먼트는 제로 패딩하고 매니페스트의 원본 크기로 잘라낸다.

`segCount = 1` 이 자연스럽게 소파일 케이스를 흡수하므로 **크기 분기가 존재하지 않는다.**

### F. 암호화 — 옵션, 기본 off, 메타데이터도 보호

기본 플로우는 마찰 없이. 송신 화면에 **"이 QR은 촬영되면 누구나 읽을 수 있습니다 — 공공장소라면 암호화를 켜세요"** 상시 배지. 암호화 ON이면 파일명·MIME도 암호문 안에 들어간다 (D11).

### G. 방출 스케줄 — 전 세그먼트 라운드로빈 무한 루프 (D9)

§ 핵심 설계의 방출 순서 참조. 송신자 메모리 O(1), 모든 수신자 오버헤드 1.0×, 유휴 없음.

### H. 전송 완료 신호 — 없음이 의도이며, UX로 보완한다

**단방향 채널이므로 송신자는 수신 완료를 알 방법이 원천적으로 없다.** rev2는 이걸 명시하지 않아 누락처럼 보였다. 의도된 설계이며 다음으로 보완한다:

- 송신 화면에 **"1회 순환 완료 · N회차 재생 중"** 카운터 표시 → 사람이 판단 근거를 가짐
- 수신 완료 시 수신 기기에서 **소리 + 햅틱 + 전체 화면 체크마크** → 송신자가 육안으로 인지
- 역방향 ACK 채널(오디오 또는 QR)은 **P4 카드**로 기록만 (아래 참조)

## 아키텍처 — 모듈 경계

AC-1이 `npm test` in-process 루프백이고 SP-B가 순수 시뮬레이션인 시점에서, **브라우저 무관 코어는 선택이 아니라 전제**다.

```
src/core/            ← DOM·브라우저 API 0. Node + vitest. AC-1(a~f)·AC-2(자가계측)·SP-B 전부 여기서 실행
  rs/                GF(256) 산술, systematic RS 인코더/erasure 디코더
  schedule/          라운드로빈 방출기, 캐러셀 순서, 셔플
  frame/             24B 헤더 pack/unpack (D2), crc32
  base44/            44자 알파벳 코덱 (D8)
  segment/           분할(확정 E), 매니페스트 직렬화(D3/D11), 이어받기 비트맵 직렬화(AC-7)
  pipeline/          encodeStream: bytes → payload 무한 이터레이터
                     decodeSink:   payload → 상태 → bytes
src/platform/        ← 브라우저 어댑터, 최대한 얇게
  detect/            BarcodeDetector | zxing-wasm 이중 경로 → 공통 인터페이스 (ImageBitmapSource) => string[]
  camera/            getUserMedia, 프레임 그랩
  qr-render/         payload string → canvas (alphanumeric 모드 강제)
  storage/           IndexedDB (AC-7)
  crypto/            PBKDF2 / AES-GCM (A4), 스트리밍 SHA-256 (D10)
  compress/          CompressionStream 래퍼 (A3)
src/app/             ← React + Zustand + PWA (AC-6)
```

**핵심 속성**: 와이어 포맷 계약(헤더·base44·매니페스트·스케줄)이 전부 `core/` 에 있어 송·수신이 같은 코드로 대칭 검증되고, AC-1 루프백이 `pipeline/` 두 함수의 직결로 자연스럽게 성립한다.

### 마일스톤 — 불확실성 최속 소진 순서

| | 내용 | 기기 | 해소하는 리스크 |
|---|---|---|---|
| **M1** | `core/rs` + `core/schedule` = SP-B 시뮬레이터 | 0대 | 최대 재설계 리스크(코딩 방식) + 최대 모델 구멍(스케줄러×캡처율) 동시 |
| **M2** | SP-A 충실도 페이지 (M1과 병렬) | 원격 | D8 확정 |
| **M3** | `core/frame` + `base44` + `segment` + `pipeline` → AC-1a~f Node green | 0대 | **여기까지 브라우저 코드 0줄** |
| **M4** | `platform/` 최소 송·수신 페이지 → **첫 광학 전송** | 보유 기기 | fps A/B가 부산물로 산출. AC-1e Playwright 편입 |
| **M5** | 스트리밍·메모리(AC-2), 실측 게이트(AC-3) → **스코프 재확정** | 다기기 | 확정 C |
| **M6** | app/PWA(AC-6), 이어받기(AC-7), 암호화(AC-5), 코칭 UI → AC-4 → AC-9 | 다기기 | |

> M4의 최소 페이지에 **fps 카운터·무결성 표시를 처음부터 내장**할 것. AC-3/AC-4의 다기기 실측이 반복 비용의 최대 항목이므로 측정을 상시화한다.

**규모 감각** (1인 개발): `core/` 10~15 파일 — 난이도 중심은 RS 디코더와 스케줄러이나 M1에서 시뮬레이터로 먼저 태어나 리스크가 전진 배치된다. `platform/` 8~12 파일 — 최난 구간은 iOS Safari 카메라 파이프라인이며 코드량보다 기기 디버깅 시간이 지배적. `app/` 15~25 파일 — 난이도 낮으나 시간 흡수원.

## Acceptance criteria

### AC-0 · Stage 0 (차단성)

SP-A · SP-B 결과 문서가 존재하고 각각의 "실패 시 파급" 발동 여부가 명시될 것. **AC-1 이후는 Stage 0 통과 후에만 유효.**

### AC-1 · 자동 루프백 스위트 (`npm test`, Node)

인코더 출력을 디코더에 in-process 주입. 전 시나리오에서 복원 sha256이 원본과 일치.

| ID | 시나리오 |
|---|---|
| AC-1a | 무손실 — 전 심볼 순서대로 |
| AC-1b | 랜덤 30% 프레임 드롭 |
| AC-1c | **중간 진입** — 무한 방출 스트림의 임의 오프셋(0~10,000 프레임)부터 수신 시작 |
| AC-1d | CRC 손상 프레임 10% 주입 (수신자가 조용히 폐기하고 계속) |
| **AC-1f** | **스케줄러 × 캡처율** — `segCount = 90`, 캡처율 r ∈ {0.4, 0.8} 서브샘플링, 임의 오프셋 진입, 무한 루프. **오버헤드 ≤ 1.3× (p95) 이고 수신자 피크 메모리 ≤ 파일 크기 × 2** |
| **AC-1g** | **압축 경로** — gzip으로 30% 이상 줄어드는 페이로드 1건. A3의 "5% 미만 스킵" 분기가 아닌 실제 압축 경로가 실행될 것 |
| **AC-1h** | **스트림 재시작** — 50% 진행 중 새 `streamId` 도착 시 수신자 동작이 정의대로 (기존 진행분 보존 + "다른 전송이 감지됨" 프롬프트) |

> ⚠️ AC-1은 **QR 렌더 → 카메라 → 디코더 왕복을 정의상 건너뛴다.** SP-A / AC-1e가 그 구간을 담당하며, AC-1 통과가 그 구간의 안전을 의미하지 않는다.

### AC-1e · 인코딩 계층 왕복 (SP-A 하네스의 제품 편입)

`bytes → base44 → QR alphanumeric → 이미지 → QR 디코딩 → base44 → bytes` 를 이미지 왕복 포함으로 검증.

- **케이스 설계가 횟수보다 우선**: 44자 알파벳 전수 스윕, 경계 문자 인접 패턴, 만재 프레임(1,234B) 랜덤 — 적대적 케이스 ~100개를 먼저 고정하고, 그 위에 랜덤 10,000회를 얹는다
- **CI(Linux headless)에는 `BarcodeDetector` 가 없다.** 이중 경로 중 `BarcodeDetector` 다리는 로컬/실기기 수동임을 명시. CI는 `zxing-wasm` 경로만 게이트한다

### AC-2 · 세그먼트 경계 회귀 + 메모리 상수성

합성 데이터 `1KB / segmentSize−1 / segmentSize / segmentSize+1 / 5MB / 20MB` 각각 분할→인코딩→복원 sha256 일치.

**메모리 측정 — 자가 계측이 1차 게이트** (rev2는 측정 방법이 역전돼 있었다):
- `measureUserAgentSpecificMemory()` 는 realm 전체 측정이라 "심볼 버퍼 상주량"을 분리하지 못하고 GC 타이밍에 취약하다
- **1차**: 심볼 버퍼는 자기 자료구조이므로 **바이트 카운팅 자가 계측**. Node에서 결정론적으로 실행되므로 `5MB` 대 `20MB` 케이스의 송신자 버퍼 차이 < 10% 비교가 공짜로 성립
- **2차**: `measureUserAgentSpecificMemory()` 는 "숨은 복사본이 없는가" sanity 로만 사용 (COOP/COEP Playwright 셋업 1회)
- 게이트: **송신자 심볼 버퍼가 파일 크기와 무관하게 1 MB 이하** (D9로 O(1)이 됐으므로 rev2의 3MB에서 하향)

### AC-3 · 성능 게이트

| 항목 | 목표 |
|---|---|
| Android Chrome 수신 디코드율 (`BarcodeDetector` + base44) | ≥ **8 fps** |
| iOS Safari 수신 디코드율 (`zxing-wasm`) | ≥ **4 fps** |
| 데스크톱 Chrome 웹캠 수신 | ≥ **6 fps** |
| **세그먼트당** 오버헤드 (복원까지 수신 심볼 ÷ K) — 정상 조준 | ≤ **1.05×** |
| 세그먼트당 오버헤드 — 캡처율 0.4 + 손실 20% | ≤ **1.3×** (p95) |
| 프레임 인코딩 (RS 심볼 생성 + base44 + QR 렌더) | ≤ **8 ms** |
| 1MB 파일 데스크톱Chrome→Android 실측 | ≤ **2.5분**, sha256 일치 |

> `K` 는 **세그먼트당** 소스 심볼 수. SP-B가 이 게이트의 달성 가능성을 사전 검증하고 `(K, N)` 을 확정한다.

### AC-4 · 실기기 스모크 매트릭스

4개 조합 전부 1MB 파일 무결성 일치:
`데스크톱Chrome→Android` / `데스크톱Chrome→iOS` / `Android→iOS` / `iOS→데스크톱 웹캠`

### AC-4L · 장시간 실전송 (신설)

**10MB 파일 1회 완주** (데스크톱Chrome→iOS Safari, 약 36분). 루프백으로는 원리적으로 잡을 수 없는 것을 검증한다:
- 열 스로틀링에 의한 디코드율 저하 곡선 기록
- iOS Safari 메모리 압박 / 탭 파기 발생 여부
- 오토포커스 드리프트
- Wake Lock 유지 여부
- 완료 시 sha256 일치

> rev2는 OQ-5에서 이 공백을 스스로 지적하고도 AC로 닫지 않았다.

### AC-5 · 암호화 라운드트립

패스프레이즈 ON 전송 → 올바른 키로 복원 시 sha256 일치. 잘못된 패스프레이즈는 **10초 이내** "복호화 실패 — 패스프레이즈를 확인하세요". PBKDF2 600k iter가 저사양에서 수 초 걸리므로 진행 중 "키 유도 중" 스피너로 정상 대기와 구분.
**추가**: 암호화 ON일 때 매니페스트 평문에 파일명·MIME가 **없을 것** (D11) — 프레임 덤프로 검증.

### AC-6 · 오프라인 동작

네트워크 차단 후 PWA 재방문 시 다음이 전부 동작:
- 파일 드롭 → QR 재생 (송신)
- 카메라 기동 → 수신 → 복원 → 뷰어 → 다운로드
- **`zxing-wasm` 바이너리가 Service Worker precache에 포함될 것** — 빠지면 오프라인 수신이 iOS에서 전면 실패
- 암호화 on/off 양쪽

### AC-7 · 이어받기

수신 50% 지점에서 탭 종료 → 재진입 시 진행률 보존, 이어서 완료. **직렬화 포맷**: 세그먼트당 N비트 수신 비트맵 + 미복원 세그먼트의 리페어 심볼 원본 + 매니페스트.

### AC-9 · 온보딩 — 게이트가 아닌 정성 관찰

n=3에 2/3 게이트는 1명 차이로 뒤집혀 통계적으로 무의미하다. **AC-4 통과 후 릴리스 전 정성 관찰 세션**으로 재정의한다.
- 3명에게 송신 화면만 보여주고 안내 없이 수신 완료까지 관찰
- 산출물은 pass/fail이 아니라 **"어디서 막혔는가" 목록**
- 절차·질문지는 `.hako/specs/onboarding-test.md` 로 고정 (재실행성)

## Open questions

### OQ-1 · `BarcodeDetector` 의 alphanumeric 정규화 (트림 외)

base44로 공백 리스크는 제거됐으나 다른 정규화(대소문자·유니코드 정규화)가 실존하는지 미확인.
- **닫는 방법**: SP-A. 실패 시 `zxing-wasm` 단일 경로 (스펙 표면적 축소).

### OQ-2 · `(K, N)` 확정값과 캐러셀 RS의 실측 오버헤드

`r_min × N ≥ K` 제약 하에서 K를 얼마로 둘 것인가. iOS가 3fps만 낸다면 r_min = 0.3이 되어 K ≤ 76으로 내려가고 세그먼트가 92KB로 작아진다 (세그먼트 수 증가 → 매니페스트·헤더 오버헤드 상승).
- **닫는 방법**: SP-B + M4의 iOS fps 실측.

### OQ-3 · `BarcodeDetector` 이중 경로가 유지할 가치가 있는가

이득 플랫폼은 **Android Chrome 하나**다 (iOS·Firefox 미지원, 데스크톱 Chrome은 백엔드가 다름). 그 하나를 위해 전 플랫폼이 이중 경로 코드 + SP-A + AC-1e + OQ-1 리스크를 진다. 다만 ML Kit는 블러·글레어·사각에서 **프레임당 디코드 성공률**이 zxing보다 현저히 좋다고 알려져 있어, 실조준 조건에서 "8fps vs 7fps"가 아니라 "8fps vs 2~3fps 유효"일 수 있다.
- **닫는 방법**: M4에서 동일 기기·동일 광학 조건 A/B — `BarcodeDetector+base44` vs `zxing-wasm+byte`, **정조준 / 약블러 / 약글레어 3조건** × 유효 디코드율. 격차 15% 이내면 zxing 단일 경로로 접는다.
- 부수: `zxing-wasm` 은 luma 입력을 받으므로 **OffscreenCanvas/WebGL 그레이스케일 + ROI 크롭 전처리**의 fps 이득도 같이 측정할 것.

## Constraints

- **기술**: React + TypeScript + Vite, PWA, 정적 호스팅. 서버 사이드 코드 금지 (D5).
- **브라우저**: Chrome(데스크톱/Android), Safari(iOS/macOS), Firefox, Edge. iOS Safari가 최저 성능 기준선.
- **인코딩**: base44 + alphanumeric 모드 고정 (D8). byte 모드 금지.
- **채널 코딩**: GF(256) systematic RS, N ≤ 255 (D1).
- **성능**: AC-3 수치 게이트.
- **프라이버시**: 파일 데이터가 네트워크로 나가는 경로가 코드상 존재해서는 안 됨. 암호화 시 메타데이터도 보호 (D11).
- **접근성**: 카메라 권한 거부 시 복구 안내. 저조도·손떨림 코칭 UI.

## Out of scope

- **B2B / 망분리 온프렘 제품** — 감사 로그, 정책 엔진, 온프렘 패키징
- **CLI / SDK / 라이브러리 배포** — 웹앱 단일 산출물
- **역방향 ACK 채널 (QR 듀플렉스 / 오디오)** — P4 카드 (아래)
- **2×2 이상 타일 그리드** — 실험 트랙. D12 추상화만 남김
- **컬러 QR / JAB code / 커스텀 래스터 코드** — 표준 QR만
- **RGB 3채널 독립 데이터** — 서브픽셀 × Bayer × AWB × 색수차 누화. 표준 디코더 전량 포기가 되어 리스크 예산 초과
- **프레임 간 차분 인코딩** — 롤링 셔터·프레임 블렌딩이 차분을 파괴하고, "모든 프레임 독립 디코드"라는 중간진입(AC-1c)의 전제 자체를 깸
- **계정, 서버 저장, 전송 이력 동기화** — 서버 없음
- **송신 측 이어받기** — 확정 B의 20MB 소프트 상한으로 불필요해짐 (메모리 상주로 충분)
